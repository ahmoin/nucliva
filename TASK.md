## 📌 Devpost Form Answers

Which model(s) did you use, and why did you choose that size/variant?

I used all three sizes of NVIDIA Nemotron 3 on Nebius Token Factory, each matched to a job. Nano (30B, 3B active) powers inline autocomplete, which runs on almost every pause in typing, so speed matters most and I turn thinking off. Super (120B, 12B active) handles the structured, high-volume work: reading facts out of paragraphs for the ripple feature, rewriting sentences that depend on a changed fact, analyzing the tone of a user's writing samples, planning agent runs, and turning a document into a matching sheet and slide deck. Ultra (550B, 55B active) writes everything in the user's voice: document edits, research drafts and the agent's main document, where writing quality matters most. I also use Qwen3 Embedding 8B on Token Factory for the pgvector embeddings.

How would you rate Nemotron's output quality for your use case? (1 = Poor, 10 = Excellent)

9. Ultra's long-form writing in a matched voice was strong, instruction following was reliable once the task was tightly specified, and structured JSON output against my schemas worked well. Where it fell short: my first fact-extraction design asked the model to invent fact IDs and read exact values, and it scored 0 on my evaluation because it hallucinated IDs and slightly wrong numbers. I redesigned it so the model only names facts and points at where they are stated, while code reads the values, makes the IDs and does all the arithmetic. After that it got 30 of 30 suggestions right over 5 runs. Out of the box, the reasoning mode also made short replies slow.

Did you fine-tune, prompt-engineer, or use Nemotron out of the box? What was your approach?

Out of the box, with prompt engineering and system design, and no fine-tuning. Every structured call returns JSON validated against a Zod schema, with a fallback to a plain reply if parsing fails. For voice matching, the user's own writing samples are retrieved from pgvector and put in the prompt along with extracted tone markers. I split the work so the model handles understanding and deterministic code handles math and formatting. Thinking is turned off per call for latency-sensitive tasks and kept on for writing. A small evaluation script measures precision and recall, so prompt changes are checked rather than eyeballed.

How did Nemotron's performance compare to other models you've used for similar tasks?

For writing in a specific person's voice, Nemotron 3 Ultra held up well against the frontier models I have used before. It followed tone and structure closely and produced natural prose. Where it stood out was the family as a whole: having Nano, Super and Ultra trained the same way meant I could move a task between sizes and get consistent behavior, which is hard to do when mixing models from different providers. Nano was fast enough for keystroke-level autocomplete, something that would normally need a separate small model, and Super handled structured extraction as well as the larger proprietary models I tried, at a fraction of the latency. The trade-off was that reasoning mode adds noticeable latency on short tasks, so I learned to turn it off where speed matters. Because Nemotron is open, I know exactly which model serves each feature and can rely on it not changing underneath me.

Which Nebius platform capabilities were most valuable to your project and how?

The OpenAI-compatible Token Factory API was the most valuable. I did not run any GPU instances myself: all inference goes through Token Factory's managed endpoint, using LangChain's standard OpenAI client with only the base URL changed. Moving a feature between Nano, Super and Ultra is a one-word change in the code, which let me try each task on each size quickly. Token Factory passes options through to the model's chat template, so I turn thinking off per request, which cut autocomplete and fact-reading latency sharply. Embeddings run on the same account and key, so there is one provider to set up. The Suite agent, which researches and writes a linked doc, sheet and deck, runs as a containerized Nebius Serverless AI job, started through the Nebius REST API with a service account while the app polls the job's state. Scaling is handled by Token Factory, so I never had to provision or autoscale anything.

How likely are you to recommend running Nemotron on Nebius to other developers? (1 = Unlikely, 10 = Highly Likely)

10. Zero infrastructure, an OpenAI-compatible API, and three model sizes behind one key made it very quick to get started, and I would point any developer building with open models here first. Two things would make it even easier: clearer docs on per-model options such as enable_thinking, and an official JavaScript SDK for the Serverless API. Right now I sign the service account JWT and call the REST API by hand.

How would you rate your experience running Nemotron inference on Nebius compared to previous cloud or local development environments? (1 = Poor, 10 = Excellent)

9. Compared with running open models locally, there is no GPU, no model download and no serving stack, and a model the size of Ultra is not something I could run locally at all. Compared with other hosted APIs, switching over was trivial because of OpenAI compatibility. The main cost was latency when reasoning was on, which I solved per call.

What additional features or improvements would have made the Nemotron on Nebius experience more effective for your project?

Prompt caching for repeated system prompts would help the most. Every draft sends the same writing samples and tone markers to match the user's voice, so caching that prefix would cut both latency and cost on every request. Second, a strict JSON schema mode that guarantees valid output: I validate every structured reply with Zod and keep a fallback path for replies that do not parse, and a guarantee at the API level would remove that code. Third, per-request latency and token usage in the Token Factory dashboard, broken down by model, would have made choosing between Nano, Super and Ultra for each task faster than timing it myself. On the Serverless side, a webhook or event when a job finishes, instead of polling its state, plus faster cold starts and a shorter minimum timeout for CPU jobs that only run for a few minutes, would make it a natural fit for short background agent runs. An official JavaScript SDK covering both Token Factory and Serverless, including service account sign-in, would tie it all together.

What do you most hope to see from the Nemotron team next?

Faster time to first token for Ultra with reasoning on, or a light reasoning setting between off and full. Even more reliable structured output on long, nested schemas. And a small Nemotron embedding model, so the whole stack could run on Nemotron.

Did you use Tavily in your project?

Yes. Tavily is the web-grounding layer. In the editor chat, research requests search the live web with Tavily, the sources found are shown while the answer is written, and the draft cites them with numbered sources when asked. The Suite agent runs up to four Tavily searches per request and builds the doc, sheet and deck from those sources, so the numbers can be traced back.

Which AI tools have you leveraged while working on this project?

In the product: NVIDIA Nemotron (Nano, Super and Ultra) and Qwen3 Embedding 8B on Nebius Token Factory, Nebius Serverless AI, Tavily for web search, LangChain for orchestration and LangSmith for tracing. For development: Claude Code as a coding assistant.

Describe the level of learning you/your team derived from the project

High. The biggest lesson was where models should and should not be trusted: moving arithmetic, ID creation and value reading out of the model and into code took the fact-tracking feature from 0 percent to 100 percent on my evaluation. I also learned to pick model sizes per task instead of using one model for everything, to control reasoning to manage latency, to design AI edits as suggestions the user reviews rather than silent rewrites, and to run background agents on serverless infrastructure.

Did you gain AI value that you can use in your career?

Yes. I gained practical skills in building AI products end to end: retrieval with pgvector, structured outputs, grounding with web search, evaluation-driven prompt work, routing between models and serverless agent jobs. Above all, I learned the habit of measuring AI features with a real evaluation instead of trusting demos, which carries straight into professional work.
